# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

`pigeon` is a Zephyr RTOS module: the on-device client library for **PidgeIoT**. It runs on the physical asset/gateway and is the counterpart to the `dovecote` edge backend and `capsules` shared models in the main PidgeIoT monorepo at **`~/pidgeiot`**. This repo is a standalone Zephyr module (own git history, no path/workspace relationship to `~/pidgeiot`) — the two only need to agree on the wire protocol.

**When working on anything protocol-, auth-, or connector-shaped here, read `~/pidgeiot/CLAUDE.md` first and cross-check against these backend source files**, since this device library must stay wire-compatible with them:

- `~/pidgeiot/capsules/src/lib.rs` — the `Connector` enum (`Https(HttpsConfig)` / `Coap(CoapConfig)` / `Mqtt(MqttConfig)` / `Nidd(NiddConfig)`) this library's `enum pigeon_connector_type` and `struct pigeon_config` must match the shape of. `HttpsConfig`/`CoapConfig` carry `endpoint` + `token` (+ DTLS PSK identity/secret for CoAP); on this side, `endpoint`/`token` are build-time `CONFIG_PIGEON_ENDPOINT`/`CONFIG_PIGEON_TOKEN` Kconfig strings rather than runtime struct fields — `PIGEON_CONNECTOR_TYPE` is already a build-time choice, so only one endpoint/token pair is ever live. PSK fields stay in `struct pigeon_coap_config` since they're optional per-device.
- `~/pidgeiot/dovecote/src/objects/pigeons.rs` (`get_shadow_device`) / `src/objects/helpers.rs` (`verify_device_token`) — devices authenticate with an opaque, **not-JWT** bearer credential, `Bearer`-prefixed: a 69-byte binary blob (`version | expires_at | Ed25519 signature`), base64url-encoded. It carries no pigeon-id claim of its own — the backend verifies it against whichever pigeon's own stored `device_public_key` the request's URL path resolves to, so this library never needs to embed or check its own identity beyond sending the right endpoint + token pair. (Rewritten 2026-07-15, replacing an earlier Ed25519-signed-JWT scheme (`require_device_auth`) that had two successive bugs — a `sub`-vs-`aud` claim mismatch, then a follow-on ACL check that 403'd every device request — both mooted by this rewrite rather than patched.) Whatever this library sends as `auth_token` must satisfy `verify_device_token`.
- `~/pidgeiot/dovecote/src/objects/pigeons.rs` (`build_http_endpoint`/`build_coap_endpoint`, and the `/pigeon/shadow/get` (dashboard), `/pigeon/device/shadow` (device, no `X-User-Id`/ACL check — see above), `/pigeon/shadow/update` routes) — defines the actual endpoint URL shapes (`https://api.pidgeiot.com/device/pigeons/{id}`, `coaps://api.pidgeiot.com/device/pigeons/{id}`) and the shadow document (`target_config`/`current_config` + version counters) this library syncs against.
- The backend issues/rotates the device token via `token/refresh`, which mints a **brand-new keypair** and overwrites the pigeon's stored public key — this revokes every previously-issued token for that pigeon, not just the one being replaced. Out of scope for this library to mint or verify tokens, only to present whatever it's given.
- **CoAP transport (updated 2026-08-10, task #2):** the CoAP connector now has a build-time transport choice — CoAP-over-DTLS/UDP (RFC 7252, `coaps://`, `CONFIG_PIGEON_COAP_TRANSPORT_UDP`, the PRIMARY transport for constrained battery/cellular devices per product direction) alongside the original CoAP-over-TLS/TCP (RFC 8323, `coaps+tcp://`, `CONFIG_PIGEON_COAP_TRANSPORT_TCP`, still the default so existing builds don't change). `capsules::CoapConfig`'s `tls_psk_identity`/`tls_psk_secret` naming matches both (one PSK pair feeds whichever transport is compiled in); `build_coap_endpoint` on the backend still only emits `coaps+tcp://` — the endpoint scheme a provisioned pigeon carries must match the device's compiled-in transport (validated loudly at first use), so the terminator task (pidgeiot task #1) owns adding `coaps://` endpoint minting. dovecote still has no CoAP listener deployed; protocol conformance is verified against libcoap instead (see pigeon-examples' README "CoAP over DTLS" section for the full 2026-08-10 e2e matrix).

## Current state

`src/pigeon_core.c`: `pigeon_init` implemented; `pigeon_telemetry_set()` queues key/values into a batched, latest-value-per-key pending store (`CONFIG_PIGEON_TELEMETRY_MAX_KEYS` slots, default 8; a full store rejects a NEW key with `-ENOMEM` rather than evicting), and `pigeon_telemetry_flush()` drains ALL pending keys as ONE flat JSON report over the active transport's `pigeon_transport_report_telemetry()` (or one WS telemetry frame — WS-first with HTTPS fallback, unchanged). Clear-on-success per report: a failed send keeps its keys queued, a successful one clears exactly the keys it carried — never lost, never double-sent. The body is built centrally in `pigeon_core.c` (`pigeon_json_escape()` per key/val, `PIGEON_TELEMETRY_BODY_MAX` in `pigeon_internal.h` sized so a full escape-free batch always fits one report; pathologically escape-heavy values split into consecutive reports rather than truncating). `pigeon_set_shadow_param()`/`pigeon_shadow_flush()` remain as thin backward-compatible wrappers (added 2026-07-29, batch-telemetry task) — existing consumers (e.g. the departure board) keep working, but with the semantic upgrade that multiple distinct keys now coexist instead of overwriting a single slot.

**Batched telemetry (`CONFIG_PIGEON_TELEMETRY_BATCH`, opt-in, added 2026-08-24, task #22, HTTPS only):** the device half of dovecote's batched report body (`{"reports":[{"age_secs":N,"metrics":{...}},...]}`, `docs/api.md`'s telemetry section is the contract). With it on, `pigeon_telemetry_flush()` changes meaning rather than gaining a sibling: it closes the pending keys into one timestamped *reading* and delivers the accumulated readings only when a batch is due (`_DEPTH` readings, the oldest reaching `_MAX_AGE_SEC`, or the arena three-quarters full) — so an app already calling flush on its sampling cadence gets batching with no code change, and a call that only buffers returns 0 because nothing was lost. `pigeon_telemetry_record()` (close a reading without delivering), `pigeon_telemetry_flush_now()` (deliver before a reboot/FOTA swap) and `pigeon_telemetry_batch_pending()` round out the API and compile to inlines when the option is off. **Why this exists is COGS, not the customer's bill**: a delivery costs the platform one worker request, auth hop, queue message, DO round trip and history write regardless of how many readings ride it, while the billable count follows the readings — six readings per delivery is ~3.4x cheaper to serve and bills the account exactly what six reports would have. **Why `age_secs` and not a timestamp**: no wall clock here (no RTC, NTP removed in 0.13.6), so ages are `k_uptime_get()` deltas, rounded to nearest and clamped to the platform's own 24h backdate window. The buffer (`src/pigeon_telemetry_batch.{c,h}`, transport- and clock-free, `now_ms` passed in so `tests/telemetry_batch`'s 24 native_sim cases need no device) is a flat arena of already-escaped metrics fragments plus a descriptor array, both sized from Kconfig at compile time; overflow drops the OLDEST reading, counted and warned once per flush, because the freshest value is what a dashboard, an alert rule and a connection badge all read. Failure handling splits the batch from the moment: a 429 honors the server's `Retry-After` (this is what a free-tier account meets once its pooled allowance is spent) or falls back to jittered exponential backoff, while a 400/413 — or an `-EMSGSIZE` no transport could frame — drops the batch loudly, since identical bytes are refused identically forever and keeping them would stall every later reading. Over `CONFIG_PIGEON_WS` the batch rides the same telemetry frame with `reports` in place of `metrics`, still fire-and-forget — which is exactly why the caps are BUILD_ASSERTed here rather than relied on to come back as an error. **Watchdog interaction**: only a completed round trip feeds it (a buffered reading proves nothing about the link), so on a `CONFIG_PIGEON_WATCHDOG` build without `CONFIG_PIGEON_WS` a `_MAX_AGE_SEC` at or past `CONFIG_PIGEON_WATCHDOG_TIMEOUT_SEC` is a build error rather than a reboot loop found in the field. Live-verified against `dovecote-staging` 2026-08-24 with the bytes the library itself frames: a 6-reading/5-key batch `202`d, the latest-value store took the newest reading's values, and history reconstructed all six points at exactly the 10s spacing the ages encoded; a 65-reading batch `400`d whole, confirming the fatal-status classification. **CoAP is deliberately out of scope** — the terminator frames requests differently and no batched CoAP shape has been specified; those builds keep the flat per-flush report. Also in the same pass, and independent of the option: the telemetry POST now surfaces its HTTP status and any `Retry-After` through the same `struct pigeon_http_result` the FOTA download uses (the capture was hoisted out of the FOTA ifdef; `src/pigeon_http_status.c` is compiled unconditionally now), and returns **-EAGAIN on a 429** instead of a bare `-EIO` on every non-2xx.

`src/pigeon_https.c` implements all three device-facing operations, each device-authenticated with `Authorization: Bearer <CONFIG_PIGEON_TOKEN>` via Zephyr's `http_client_req()`:
- `pigeon_shadow_get()` — GET `<CONFIG_PIGEON_ENDPOINT>/shadow`, decoded with the declarative JSON parser (`zephyr/data/json.h`) into `target_version`/`current_version`/`target_config`/`current_config`/`updated_at`. Requires `CONFIG_PIGEON_HTTPS_SEC_TAG` (default 1) to match whatever sec_tag the app provisioned its CA cert under.
- `pigeon_telemetry_flush()` / `pigeon_transport_report_telemetry()` — POST `<endpoint>/telemetry`, body a flat JSON object of every pending key (`{"k1":"v1","k2":"v2",...}`), matching dovecote's `report_telemetry_device` (latest-value-per-key store; the route always accepted multi-key bodies — only the device library used to serialize one key per request).
- `pigeon_shadow_report()` — POST `<endpoint>/shadow`, body `{"current_config":<raw JSON>,"current_version":<int>}`, matching `capsules::PigeonShadowReportRequest`/dovecote's `report_shadow_device`. Call after applying a `target_config` fetched via `pigeon_shadow_get()`.

The CoAP connector (split 2026-08-10, task #2) is `src/pigeon_coap.c` (transport-agnostic core: endpoint parse with per-transport scheme validation, shared request-option building — **no credential rides in any CoAP message**: the PSK handshake is the device's entire authentication, the platform maps the handshake identity (the pigeon's id) to the pigeon and holds the bearer token server-side, so CoAP builds may leave `CONFIG_PIGEON_TOKEN` empty (`pigeon_core.c` only enforces it on HTTPS builds) — shadow JSON decode, the public `pigeon_shadow_get()`/`pigeon_shadow_report()`/telemetry entry points) plus exactly one compiled-in transport behind `pigeon_coap_transport_exchange()` (`src/pigeon_coap_internal.h`):
- `src/pigeon_coap_tcp.c` — RFC 8323 TLS/TCP framing, one connection per exchange. Now sends the RFC 8323-mandatory CSM on connect and skips/answers the peer's signaling frames (CSM/Ping/Pong) — found the day the path first ran against a real CoAP server (libcoap greets with 7.01; dovecote never listened, so the MUST had never been exercised). Live-verified e2e against libcoap's TLS/TCP listener 2026-08-10 (first ever — including the previously-unchanged `coap_tcp_init` sample).
- `src/pigeon_coap_udp.c` — RFC 7252 CoAP-over-DTLS/UDP on ONE long-lived PSK DTLS session (handshake paid once; any exchange failure closes the socket so the next exchange re-handshakes — the no-CID NAT-rebind recovery path). Message layer: CON requests with retransmission timing from Zephyr's own `coap_pending` helpers (governed by the standard `CONFIG_COAP_INIT_ACK_TIMEOUT_MS`/`_ACK_RANDOM_PERCENT`/`_BACKOFF_PERCENT`/`_MAX_RETRANSMIT`, no new knobs), and matching/dedup logic (piggybacked vs separate responses, Empty-ACK handling, duplicate re-ACK-without-redeliver, RST) factored pure into `src/pigeon_coap_udp_match.c` — unit-tested in `tests/coap_udp` (16 ztest cases, native_sim). DTLS Connection ID (RFC 9146, `CONFIG_PIGEON_COAP_DTLS_CID`, default n — the platform's CoAP terminator can't negotiate CID yet, so the default doesn't advertise a capability the server side can't honor; the device plumbing is complete and, when enabled, is) offered as `TLS_DTLS_CID_SUPPORTED` (empty own CID — the client-behind-carrier-NAT shape) through the one portable sockopt both backends honor; verified live: CID session survived a mid-session address rebind with zero re-handshake against libcoap-mbedTLS, and the CID-less fallback (timeout → close → re-handshake) against libcoap-OpenSSL. **Do not trust Zephyr's `TLS_DTLS_CID_STATUS` as a positive signal on native builds** — it reads uninitialized stack when the server didn't negotiate CID (upstream bug, draft report in pigeon-examples' `docs/upstream-issues/`); the nRF91 modem implements the option itself and is unaffected.
- PSK provisioning (`pigeon_coap_register_psk()`, core): `tls_credential_add()` natively, or — closing the long-documented `coap_tcp_init` known gap — `modem_key_mgmt_write()` into the nRF91 modem's own store on `CONFIG_MODEM_KEY_MGMT` builds (%CMNG IDENTITY + hex-encoded PSK, compare-before-write), done eagerly from `pigeon_init()` since the modem store only accepts writes while the modem is offline — such apps must call `pigeon_init()` BEFORE bringing LTE up (see `coap_dtls_init`'s `main.c`; not yet hardware-verified — no terminator to talk to over LTE yet).

The MQTT connector (added 2026-08-25) is `src/pigeon_mqtt.c` plus the pure decision layer `src/pigeon_mqtt_policy.{c,h}`, speaking to **pigeonhole**, PidgeIoT's MQTT broker (`~/pigeonhole`, `docs/design.md` is the authority — ADR C is the topic map, ADR D the auth model). It is the first module here that is BOTH a transport (it defines `pigeon_shadow_get`/`pigeon_shadow_report`/`pigeon_transport_report_telemetry`/`pigeon_transport_upload_logs`) and a persistent connection with a worker thread on `pigeon_ws.c`'s pattern (`pigeon_mqtt_start(cb)`/`pigeon_mqtt_stop()`/`pigeon_mqtt_connected()` in `pigeon.h`), because on this transport the session carries the requests and the pushes alike. Two consequences a reader of the other connectors will not expect: **`pigeon_shadow_get()` fetches nothing** — the broker publishes the pigeon's target shadow as a RETAINED message on `pigeon/shadow/target` and re-publishes on every dashboard write, so this connector serves whatever landed last (first call after a connect waits up to `CONFIG_PIGEON_MQTT_SHADOW_WAIT_SEC`, then `-EAGAIN`), which is the poll it replaces; and **a publish is acked end to end** (QoS 1 PUBACK means the platform took the report, so a flush returning 0 means what it does over HTTPS). Topics are session-scoped and carry no pigeon id — `pigeon/telemetry`, `pigeon/shadow/report`, `pigeon/logs` out, `pigeon/shadow/target` in — which is why **`pigeon_config.device_id` is load-bearing here and log-only everywhere else**: it is the CONNECT client id and username, must be the real 64-hex pigeon id, and (PSK builds) must equal the handshake identity, which is also why pigeon's Kconfig deliberately has no PSK-identity symbol to write it a second time. `CONFIG_PIGEON_ENDPOINT` is `mqtts://host:8883` with no path, and `mqtt://` is refused at parse time (the broker has no cleartext listener in any deploy shape). Auth is a build-time choice, `CONFIG_PIGEON_MQTT_AUTH_CERT` (verify the broker's chain, CONNECT password = `CONFIG_PIGEON_TOKEN`) or `_AUTH_PSK` (identity + `CONFIG_PIGEON_MQTT_TLS_PSK_SECRET`, no token on the wire at all — CoAP's exact rule).

Things that are ours rather than Zephyr's, because its client does not do them: **redelivery** (the client never retransmits and the broker holds no session to resume into — it answers `session_present=0` by design), so `pigeon_mqtt_policy.c`'s pending table tracks in-flight QoS 1 publishes and the connector republishes with `dup_flag` set once the session is back, the whole call bounded by `CONFIG_PIGEON_MQTT_PUBLISH_TIMEOUT_SEC` rather than each attempt; **two retry schedules**, ordinary exponential backoff for a broker that is busy, paused or unreachable versus `CONFIG_PIGEON_MQTT_AUTH_BACKOFF_SEC` (default 15 min) for a refusal that names the credentials or the identity, which cannot resolve without something happening off-device (`pigeon_mqtt_connack_retry()` reads MQTT 3.1.1 return codes and MQTT 5 reason codes in one function — the ranges cannot collide); and **the free-tier fuse's only 3.1.1 signal**, three consecutive sessions dying with a publish unacked (`PIGEON_MQTT_UNACKED_CLOSES_PERSISTENT`), which a v5 client would have been told as PUBACK 0x97 and 3.1.1 can only express by closing. `tests/mqtt_policy` covers all of that on native_sim (23 ztest cases, no broker, no network — same split `pigeon_coap_udp_match.c` uses). One behavior worth knowing because it does not exist on the other connectors: a successful `pigeon_shadow_report()` folds `current_version`/`current_config` into the CACHED shadow, since the retained value only refreshes when `target_version` changes (the broker deliberately does not re-push a device's own report-back) — without it an app comparing target against current re-applies and re-reports the same target on every pass. Found by running the sample, not by reading the code.

**Batched telemetry does not reach this connector**: `CONFIG_PIGEON_TELEMETRY_BATCH` still `depends on PIGEON_CONNECTOR_HTTPS || PIGEON_CONNECTOR_NIDD`, so an MQTT build silently drops the assignment and sends one flat report per flush -- the shape this connector is specified to send, so nothing is broken, but the symbol looks accepted in a conf file while doing nothing (the tell is the flush log line: "key(s) in one report" is flat, "reading(s) in one batch" is batched). The blocker for extending it is the QoS 0 path, not the Kconfig: the broker frames a QoS 0 publish as `{"type":"telemetry","metrics":<payload verbatim>}`, so a batched `{"reports":[...]}` body would land nested under `metrics` instead of beside `type`. Closing it means either the broker recognising a batched body and framing `reports` (its own notes record that it does not send that frame today), or this connector forcing QoS 1 whenever batching is on and giving up the frame path -- a decision spanning both sides.

**FOTA on an MQTT build** (same date): `CONFIG_PIGEON_FOTA` now depends on `PIGEON_CONNECTOR_HTTPS || PIGEON_CONNECTOR_MQTT`, and the image fetch stays HTTPS on either (megabyte-scale images, Range-chunked with device-side resume, and every MQTT-capable device has TCP+TLS — pigeonhole's design ADR C says firmware has no MQTT surface). `pigeon_https.c` is therefore compiled for an MQTT+FOTA build too, with its four connector hooks `#ifdef`'d out (the MQTT connector defines those); its endpoint comes from `CONFIG_PIGEON_FOTA_HTTPS_ENDPOINT` because `CONFIG_PIGEON_ENDPOINT` there names the broker, and both that and `CONFIG_PIGEON_TOKEN` are BUILD_ASSERTed non-empty rather than discovered at download time. `CONFIG_PIGEON_HTTPS_SEC_TAG` is available on such builds (usually a different tag from `CONFIG_PIGEON_MQTT_SEC_TAG`, and necessarily so in PSK mode where that one holds a key rather than a CA). For HTTPS builds the preprocessing is unchanged — the guards are all `#if defined(CONFIG_PIGEON_CONNECTOR_HTTPS)`, true on every existing build.

**PSK registration is shared** (`src/pigeon_psk.{c,h}`, same date): `pigeon_psk_register(sec_tag, identity, secret)` holds both stores — `tls_credential_add()` natively, `modem_key_mgmt_write()` with its digest compare-before-write on `CONFIG_MODEM_KEY_MGMT` boards — lifted out of `pigeon_coap.c` verbatim when the MQTT connector needed the same thing, modem branch included. `pigeon_coap_register_psk()`/`pigeon_mqtt_register_psk()` are now thin wrappers keeping their own already-registered latch. The modem obligation travels with it: those boards must call `pigeon_init()` BEFORE bringing the link up.

**One public-API change to know about**: the WS event enum was renamed to the connector-neutral `enum pigeon_event`/`pigeon_event_cb_t` so the MQTT connector could deliver the same three events without a second identical enum. `enum pigeon_ws_event`, `PIGEON_WS_EVENT_*` and `pigeon_ws_event_cb_t` remain as aliases (macros plus a typedef in `pigeon.h`), so existing consumers — `ws_init` among them — compile unchanged; verified by rebuilding it.

The NIDD connector is `src/pigeon_nidd.c` (`CONFIG_PIGEON_CONNECTOR_NIDD`, NCS and the nRF91 modem only): the carrier's Non-IP Data Delivery over NB-IoT, frames on a raw `AF_PACKET`/`SOCK_RAW` socket bound with `SO_BINDTOPDN` to a Non-IP PDN on the APN in `CONFIG_PIGEON_ENDPOINT` (`nidd://VZWSCEF`), which Verizon hands to ThingSpace and ThingSpace posts to dovecote. `~/pidgeiot` `docs/api.md` ("NIDD frames", "NIDD downlink and replies", "NIDD sizes and cadence") is the authority on every byte and `dovecote/src/helpers/nidd.rs` is the codec this file must match: uplink `0x01` TELEMETRY and `0x02` SHADOW_REPORT (exactly the HTTPS bodies) and `0x04` HELLO (the claim key as 32 lowercase hex); downlink `0x81` SHADOW (`<target_version> <current_version>\n` then the raw `target_config`) and `0x82` STATUS (`<code> <arg>\n`: 0 STORED, 1 PAUSED, 2 UNCLAIMED), each ending in a 16-hex tag, the first 8 bytes of HMAC-SHA256 keyed by `CONFIG_PIGEON_NIDD_CLAIM_KEY` through PSA, compared without an early exit before anything in the frame is used. Headers are decimal text because ThingSpace refuses a frame holding two adjacent NULs. Like MQTT it is both a transport (`pigeon_shadow_get`/`_report`, `pigeon_transport_report_telemetry`; the log-upload hook is deliberately not defined, since `PIGEON_LOG_UPLOAD` cannot be enabled on NIDD) and a receive channel: `pigeon_nidd_start(cb)` after the attach opens the socket, starts the `pigeon_nidd` receive thread and sends HELLO, and `pigeon_nidd_stop()` goes before the modem powers off.

**NIDD: order and the modem's memory.** `pigeon_init()` calls `pigeon_nidd_configure()` while the modem is still offline: it parses `nidd://<APN>`, imports the claim key into PSA (refusing anything but 32 lowercase hex, the form the dashboard reveals and HELLO sends), sets CID 0 back to `IPV4V6` (an earlier image may have left it Non-IP) and creates the dedicated Non-IP context (`CONFIG_PIGEON_NIDD_DEDICATED_CID`, default y; `n` makes CID 0 Non-IP for a NIDD-only plan, which then cannot enable FOTA), registers its `lte_lc` handler, requests PSM and writes eDRX, because the modem keeps both across images. It calls `lte_lc_psm_req(true)` but not `lte_lc_psm_param_set()`: lte_lc's modem-init hook already holds the app's `CONFIG_LTE_PSM_REQ_RPTAU`/`_RAT` in whichever format the app chose, and NCS parses its own default before this module's Kconfig, so the app sets `CONFIG_LTE_PSM_REQ_RPTAU="00010011"` (Verizon NB-IoT refused the 30-minute default and accepted 190 minutes). A refused PSM or eDRX write is logged, never returned, and a refused PSM request turns PSM off (`AT+CPSMS=`) rather than leave the modem on an earlier image's timers: the bench board once carried a 0 s active time that way, in which no push can page it. The connector `depends on NRF_MODEM_LIB` and *selects* `LTE_LINK_CONTROL`: depending on it is a Kconfig dependency loop back into the connector choice (`NRF_MODEM_LIB_NET_IF` selects it and depends on the connection manager, whose selectors include `NET_SOCKETS`, which the CoAP connector's `COAP` selects). It also selects the four PSA symbols the HMAC needs on TF-M and the lte_lc PDN/PSM/eDRX/RAI modules, and implies `LTE_RAI_REQ` (with the RAI module in and that off, lte_lc writes `AT%RAI=0` at every modem init).

**NIDD: locking and the socket.** One module mutex guards the state, both cached configs and the 1273-byte send buffer, held across one frame plus its `send()` (and an open, when one is needed) and never across the event callback; app-facing sends take it with a 10 s bound and answer `-EBUSY`. The `lte_lc` handler never takes it (atomics, log lines and the PDN semaphore only), because an lte_lc PDN call made under the lock completes on notifications delivered from the handler's own context; the RAI release work item takes it with `K_NO_WAIT` and skips when busy. The socket is re-opened by the next send after anything took it away: an open that finds the PDN down (a `DEACTIVATED` or `NETWORK_DETACH` event, or a `send()` that answered `ENETDOWN`/`ENETUNREACH`) closes the old socket, activates the dedicated CID and waits up to 60 s for `LTE_LC_EVT_PDN_ACTIVATED` before reading the PDN id (AT+CGACT answering is not the PDN being up), and `CTX_DESTROYED` (lte_lc frees every non-default context at `CFUN=0`) makes it re-create the context first. A failed open backs off from 60 s to 1920 s, since activating a PDN is a radio access. Every close goes through `pigeon_nidd_close_locked()`, which bumps a generation counter, so the receive thread never closes a descriptor number a newer socket now holds. The socket gets a 30 s `SO_SNDTIMEO`, since every `send()` holds the mutex and the modem's default is no timeout. `SO_KEEPOPEN` is set best-effort: it exists only on mfw_nrf91x1 2.0.1 and later, the bench nRF9160 runs mfw 1.3.7, and nothing depends on a socket outliving its PDN.

**NIDD: the rules.** Billable sends (TELEMETRY, SHADOW_REPORT) are refused without a radio access: `-ENOTCONN` before start, `-EACCES` after `STATUS UNCLAIMED 1` until reboot, `-EAGAIN` during a `PAUSED s` hold (`min(s, 86400)`, a newer PAUSED replaces it, `PAUSED 0` ends it; telemetry's `res->retry_after_sec` carries the remainder); a HELLO still due (start's failed, one unanswered after `CONFIG_PIGEON_NIDD_REPLY_WAIT_SEC`, which is how a lost claim or a lost target is recovered, or one an `UNCLAIMED 0` asked for) goes first. A verified SHADOW raises `current_version` as a maximum, clears the owed HELLO, confirms a pending report when its `current_version` is at least the version reported (`STATUS STORED n` likewise, bounded to INT32_MAX like any version), is cached only if newer (and dropped with a log line when its config is `CONFIG_PIGEON_SHADOW_CONFIG_MAX` bytes or more, although the platform accepts up to 1319) before raising `PIGEON_EVENT_SHADOW_UPDATE`, and when its `current_version` is below the version this boot reported, that report is not still inside its wait, and the same SHADOW did not bring a newer target (whose report the application sends instead, so the older one is never billed a second time or stored after it), the receive thread reports again. `UNCLAIMED 0` sends one HELLO if none went in the last hour and leaves a waiting report pending. `pigeon_shadow_report()` answers `-EDEADLK` on the receive thread, which is the event callback's, and `-ETIMEDOUT` after `CONFIG_PIGEON_NIDD_REPLY_WAIT_SEC` with the report left pending so a late confirmation still folds in. `pigeon_shadow_get()` hands out a copy of the cached target (a third static buffer, so a SHADOW arriving mid-parse cannot rewrite it), and with nothing cached waits only while a HELLO's reply is owed, up to `CONFIG_PIGEON_NIDD_SHADOW_WAIT_SEC` from that HELLO (an `UNCLAIMED 1` ends the wait), else answers `-EAGAIN` at once, so a refused key or an oversize target does not stall every wake; `current_config` is what this boot last reported (`""` before), `updated_at` is 0. Every send cancels a scheduled release and sets `RAI_ONGOING`; a frame that settles an owed reply (the SHADOW answering HELLO, or a report's confirmation or refusal) with nothing else owed schedules `RAI_NO_DATA` after `CONFIG_PIGEON_NIDD_RAI_IDLE_MS`, unless it raised a SHADOW_UPDATE the application will report on the same connection, and a telemetry-only wake leaves the release to the network. No timer in the file sends a frame: the library has no cadence, and the four radio accesses an hour are the application's to keep. `CONFIG_PIGEON_WATCHDOG` stays off in the sample, since only a delivered flush feeds it and a NIDD wake or a PAUSED hold outlasts its default timeout.

**NIDD: sizes.** Build asserts hold every uplink frame to 1273 bytes, the largest the mfw 1.3.7 modem accepted: the flat telemetry body (so `CONFIG_PIGEON_TELEMETRY_MAX_KEYS` defaults to 7 on NIDD), the batch body (`CONFIG_PIGEON_TELEMETRY_BATCH_BUF_SIZE` defaults to 1024 on NIDD; one 7-key reading at the worst-case sizes, 1157 bytes, does not fit that arena and stays pending), the report (`CONFIG_PIGEON_SHADOW_CONFIG_MAX` at most 1208), the claim key's length, and an NB-IoT network mode. Static RAM is about 5.8 KB at defaults. FOTA on NIDD is `pigeon_https.c` over the IP PDN beside the Non-IP one (so it needs the dedicated CID), from `CONFIG_PIGEON_FOTA_HTTPS_ENDPOINT` with `CONFIG_PIGEON_TOKEN`, exactly as on MQTT. The codec has no native_sim suite: it lives in the same file as the modem calls, so its evidence is the bench, every received frame re-checked byte for byte on the host. Not yet measured on the modem: what `SO_KEEPOPEN` answers on mfw 1.3.7, whether a close from another thread ends the receive thread's blocking `recv`, and what `RAI_ONGOING` does on a raw socket. The sample is `pigeon-examples` `samples/nidd_init`, nRF9160 Feather only (Verizon does not serve NIDD to the nRF9151).

`src/pigeon_log_backend.c` (added 2026-07-17, `CONFIG_PIGEON_LOG_UPLOAD`): a Zephyr dictionary-mode log backend (`CONFIG_LOG_DICTIONARY_SUPPORT`) — format strings never leave the firmware image, only compact binary-encoded log records do. Buffers records in a ring, batches and uploads them over the active transport's HTTPS/CoAP POST to `<endpoint>/logs` (dovecote's device log ingestion route, 16KiB/chunk cap). Host-side decode needs the per-build `log_dictionary.json` artifact (produced by the Zephyr build, not checked in) plus `log_parser.py`'s `colorama` dependency (undocumented upstream gap, now noted in `pigeon-examples`' README). Opt-in via Kconfig — off by default.

`src/pigeon_fota.c` (added 2026-07-18, `CONFIG_PIGEON_FOTA`; backend inverted 2026-07-22, task #8): the device half of OTA firmware updates, integrating with MCUboot. `pigeon_transport_download_firmware()` does the chunked HTTP Range GET against dovecote's `GET /device/pigeons/:id/firmware/:version` (matching the shadow's embedded `firmware` target — version/size/sha256), streaming straight into the MCUboot secondary slot rather than buffering the whole image in RAM. `pigeon_fota_apply()` verifies the assembled image's sha256 and schedules the MCUboot test-swap; the caller then reports, still naming the running version and short of the target since a staged image is not an accepted one, and triggers a graceful reboot (LTE detach first, same `CFUN=0` discipline as the rest of this library — see `pigeon-examples`' "Modem reset safety"). **Backend is now `#ifdef`-selectable, default is vendor-neutral**: plain `CONFIG_PIGEON_FOTA` uses upstream Zephyr's own `flash_img`/`stream_flash` (`flash_img_init`/`flash_img_buffered_write`) + `boot_request_upgrade(BOOT_UPGRADE_TEST)` (`zephyr/dfu/mcuboot.h` — a thin MCUboot bootutil wrapper, not an NCS API) — no `nrf` west module needed. `CONFIG_PIGEON_FOTA_NCS` (off by default) swaps in the original nRF Connect SDK `dfu_target`/`dfu_target_mcuboot` backend instead — functionally near-identical under the hood (`dfu_target_mcuboot` itself just wraps `flash_img`/`boot_request_upgrade`), kept because it's the specific path that's actually been hardware-verified (see below); `https_init` (task #8's sibling `pigeon-examples` repo, NCS-manifest sample) pins `CONFIG_PIGEON_FOTA_NCS=y` explicitly for exactly that reason, rather than silently picking up the new default. The vendor-neutral default was hardware-verified on 2026-08-26, on an ESP32-C6 running `pigeon-examples`' `wifi_init` against staging: download, sha256 verify, MCUboot test-swap, reboot into the new image, and shadow convergence reported from it. That run also found the one defect the nRF9160 e2e could never have hit. **This backend never erased the secondary slot**, because `flash_img_buffered_write()` erases only under `CONFIG_IMG_ERASE_PROGRESSIVELY` (which selects `STREAM_FLASH_ERASE`) and nothing here selected either, while NCS's own `DFU_TARGET_STREAM` selects it for the vendor path. NOR writes can only clear bits, so every image after the first one a board took was the bitwise AND of the new image and the old, and failed its own sha256 at the end of a completed download; a factory-erased slot made the first update on a fresh board work and hid it. `CONFIG_PIGEON_FOTA` now carries `select IMG_ERASE_PROGRESSIVELY if !PIGEON_FOTA_NCS`, with a `BUILD_ASSERT` in `pigeon_fota.c` refusing a build whose erase configuration is missing, and the same download that had failed its digest for four campaigns ran clean with nothing else changed. `https_init` still pins `CONFIG_PIGEON_FOTA_NCS=y`: the vendor-neutral path is verified on esp32c6, not yet on an nRF91. `pigeon_fota_confirm_boot()` must be called after the app decides the new image is healthy (`boot_write_img_confirmed()`); until that happens MCUboot reverts to the previous slot on the next N failed boots, the deliberate safety net rather than a bug, though only where the port does swap-with-revert: Espressif's is overwrite-only, so on the ESP32-C6 there is no previous slot to return to and confirming is the no-op it looks like. Not yet exercised end to end on real hardware (see `pigeon-examples`' https_init FOTA wiring notes). **Signing:** every sample that builds MCUboot now verifies an ECDSA P-256 signature, the ESP32-C6 included, where the board's own Kconfig.sysbuild would otherwise default the choice to none and leave a hash check standing in for one. The key is a build input rather than a commit: `PIGEON_BOOT_SIGNATURE_KEY_FILE`, read by `samples/Kconfig.sysbuild.signing` in `pigeon-examples`, falling back with a loud warning to MCUboot's published development key, which anyone can forge against. That symbol has to be chosen at the sysbuild level because one symbol feeds both the public half compiled into the bootloader and the private half imgtool signs with, and splitting them yields a device that refuses every update while every build looks correct.

**Download resume (`CONFIG_PIGEON_FOTA_RESUME`, added 2026-08-08, task #6; default flipped to y 2026-08-24 — the original default-off was conservatism about changing existing builds, not any recorded unreliability, and builds with no settings backend still get the old behavior automatically since the symbol can't select one for them):** motivated by the departure board's live 0.13.2 OTA campaign, where a download that died at 72% of a ~486KB image over LTE-M threw away ~45 minutes of 512B-Range-GET progress because every attempt restarted from byte 0. Design: persist only `{version, flushed_offset}` (a tiny settings/NVS record, `src/pigeon_fota_resume.{c,h}`, keys `pigeon/fota/*`) — NEVER sha256 streaming state (the digest is rebuilt on resume by re-reading the already-flushed slot bytes through `flash_area_read`, `pigeon_fota_rehash_flashed()`) and NEVER a bytes-received offset (a reboot loses the RAM-buffered write-block tail; both backends' counters are flushed-only, verified in vendored sources — `stream_flash.c`'s `flash_sync()` advances `bytes_written` only after a successful `flash_write`, and NCS `dfu_target_stream_offset_get()` returns exactly that counter, unlike `dfu_target_offset_get()` which adds the RAM tail when `CONFIG_DFU_TARGET_STREAM_SYNCHRONOUS` is off). The write-stream position itself is restored by each backend's own persistence (`DFU_TARGET_STREAM_SAVE_PROGRESS` on NCS — which also defaults `_SYNCHRONOUS` on, flushing every chunk; `STREAM_FLASH_PROGRESS` + explicit `stream_flash_progress_load/_save` upstream), because stream writes are append-only — our record binds that progress to a version and sanity-bounds it, and the reconcile (`pigeon_fota_resume_reconcile()`, pure function) resumes from the backend's flushed offset, invalidating to a from-0 restart on: version change, offset past the declared size, backend progress with no record vouching for it, an un-flushed RAM tail in a same-boot `_SYNCHRONOUS=n` retry (can't be discarded via public API), or dfu/flash-img init failure. A failed completion sha256 verify clears ALL resume state (record + backend progress + NCS first-page flatten) so the next attempt starts clean — the full-image verify stays the corruption backstop, including for a catalog image silently replaced under the same version string. `resume_from == total_size` is deliberately valid: a death between the last chunk and the verify resumes as a verify-only pass (no network at all). NCS quirks that shaped the flow: `dfu_target_init()` early-returns keeping live RAM stream state on a same-target re-init (`dfu_target.c`), so same-boot and post-reboot resume both reconcile off the queried flushed offset; transient failures now call `dfu_target_done(false)` WITHOUT `dfu_target_reset()` under resume (reset deletes the persisted progress — with resume off, both are called, exactly the old behavior). Unit suite: `tests/fota_resume` (native_sim ztest, 14 cases — reconcile matrix incl. persisted>queried/persisted<queried, plus record round-trips through real settings/NVS). One `pigeon_fota_apply()` call is still one attempt for any *app-level* attempt cap; the library's own budget (below) is the one that charges a continuation differently.

**FOTA hardening (2026-08-24, `fota-hardening` branch):** three related changes plus one latent bug.

- **HTTP status is no longer invisible.** Every non-2xx used to leave `pigeon_https.c` as a bare `-EIO`, so a rate-limited chunk looked exactly like a corrupt one. `struct pigeon_http_result` (`src/pigeon_http_status.{c,h}`) now carries the status code and any `Retry-After` back out of `pigeon_transport_download_firmware()` (optional out-param, `NULL` still fine), and **429 returns `-EAGAIN`** so even a caller ignoring the result can tell pacing from failure. Reading an arbitrary response header at all needs an application-supplied `struct http_parser_settings` on `http_request::http_cb` — Zephyr's `http_client` offers no other hook, and this needs no change to the vendored client. Only the delta-seconds `Retry-After` form is honored: the HTTP-date alternative needs a trusted wall clock these devices don't keep, so it's refused rather than guessed at. Unit suite `tests/http_status` (10 cases, native_sim) — which caught a real bug while being written: clamping to the cap *before* validating the whole value let `1999-12-31T23:59:59Z` come back as a plausible delay, so validation now runs in full first.
- **One chunk error no longer aborts the transfer.** `pigeon_fota_apply()`'s loop retries the same offset (`CONFIG_PIGEON_FOTA_CHUNK_RETRIES`, default 3) and waits out a 429 on the server's own schedule against a *separate* budget (`CONFIG_PIGEON_FOTA_RATE_LIMIT_RETRIES`, default 10), clamped by `CONFIG_PIGEON_FOTA_RETRY_AFTER_MAX_SEC` (default 60 — deliberately modest, since `pigeon_fota_apply()` blocks its calling thread and each wait adds to whatever the app's watchdog tolerates). Both counters are consecutive-at-one-offset and reset on every chunk that lands. Retries cover the network step **only**: nothing is written to flash or folded into the digest at that point, which is exactly what makes re-requesting the same bytes safe — the write stream is append-only.
- **Per-version attempt budget with a recovery story** (`CONFIG_PIGEON_FOTA_ATTEMPT_BUDGET`, `src/pigeon_fota_attempts.{c,h}`, **opt-in**). The failure being designed against isn't the runaway — it's the naive fix for it: a counter keyed on the version string alone turns three unlucky timeouts into a firmware version the device refuses *permanently*, recoverable only by republishing identical bytes under a new version string. So the count is bound to the **shadow `target_version`** that named the firmware, not the version alone. `target_version` advances when `target_config` *changes*, not on every write, so reopening the budget takes a shadow write that keeps the firmware target and alters something else; the dashboard's "Re-push firmware" action is that write (it bumps a top-level `firmware_repush` counter, outside the `firmware` object, which every decoder skips). Re-sending a byte-identical `target_config` leaves the version where it was and reopens nothing. The device can't forge the signal, since rebooting/reconnecting/re-polling all return the same value. `pigeon_fota_attempt_allowed(info, shadow->target_version)` + `pigeon_fota_attempts_clear()` in `pigeon.h`, both compiling to no-op inlines when the option is off so an app calls them unconditionally. **Attempt accounting** lives in `pigeon_fota_apply()`: a from-byte-0 campaign charges one *up front* (the boot-loop case never returns to charge later), a resume that advances the flushed offset charges nothing, a resume that ends where it began charges one. Opt-in specifically because an app with its own counter (the departure board's `FOTA_MAX_ATTEMPTS_PER_VERSION`, `app/src/net/pigeon_client.c` — **that repo, not this one**) would otherwise run two independent budgets; adopting this means deleting the local copy. Unit suite `tests/fota_attempts` (18 cases, native_sim, incl. driving the gate itself through real settings/NVS).
- **Latent bug fixed:** the download path read `http_response::cr_present` to decide whether the server confirmed an image total, but that's a transient parser flag the vendored client clears inside the same header's value callback — it always reads false once the request returns, so `*out_total` was unconditionally 0 and the server-vs-shadow size cross-check could never fire. Reads `content_range.total` directly now.

**Verification note:** `CONFIG_PIGEON_FOTA` can never be enabled on `native_sim` (`depends on BOOTLOADER_MCUBOOT`, and MCUboot doesn't support that SoC — `USE_DT_CODE_PARTITION` has no satisfiable dependency there), which is why the FOTA-adjacent logic keeps being split into MCUboot-free translation units. The full path *does* compile on **esp32c6**: `west build -b esp32c6_devkitc/esp32c6/hpcore samples/wifi_init -- -DEXTRA_CONF_FILE=<conf>` with `CONFIG_FLASH`/`FLASH_MAP`/`STREAM_FLASH`/`BOOTLOADER_MCUBOOT`/`IMG_MANAGER`/`MCUBOOT_IMG_MANAGER`/`NVS`/`SETTINGS_NVS` plus the `PIGEON_FOTA*` symbols set explicitly. Setting `CONFIG_PIGEON_FOTA=y` alone silently does nothing there — its dependencies aren't on by default and that board's build doesn't treat the unmet assignment as fatal.

`src/pigeon_ws.c` (added 2026-07-20, `CONFIG_PIGEON_WS`, task #33, hardware-verified on ESP32-C6 against staging): a persistent `wss://<CONFIG_PIGEON_ENDPOINT>/ws` push channel (dovecote task #32's device WS endpoint), additive on top of the HTTPS connector (`depends on PIGEON_CONNECTOR_HTTPS` in Kconfig) rather than a third connector choice — WS never does shadow GET/report-back, log upload, or FOTA, HTTPS still owns those. Public API (`include/pigeon.h`): `pigeon_ws_start(pigeon_ws_event_cb_t cb)` spawns a dedicated worker thread that connects and reconnects forever with backoff; `pigeon_ws_stop()` sends a real CLOSE frame and joins the thread (call before `pigeon_reboot()`); `pigeon_ws_connected()` is a point-in-time query. The callback delivers `PIGEON_WS_EVENT_CONNECTED` (app should re-`pigeon_shadow_get()` since the server sends no state snapshot on accept), `PIGEON_WS_EVENT_DISCONNECTED` (informational, reconnect is automatic), and `PIGEON_WS_EVENT_SHADOW_UPDATE` (a dashboard `PUT` landed — `shadow` param points at module-static storage valid only for the callback's duration).

Frame protocol: outbound is `{"type":"ping"}` keepalives (device-owned — the server never pings, see `CONFIG_PIGEON_WS_PING_INTERVAL_SEC`'s help text) plus opportunistic `{"type":"telemetry","metrics":{...}}` reports; inbound is `{"type":"pong"}` (resets missed-pong bookkeeping; two consecutive misses mark the connection half-open and force a reconnect) and `{"type":"shadow_update","shadow":{...}}` (server push on a dashboard write). `pigeon_core.c`'s `pigeon_shadow_flush()` tries `pigeon_ws_report_telemetry()` first when `CONFIG_PIGEON_WS` is on, falling back to the HTTPS/CoAP transport on `-ENOTCONN` — telemetry-over-WS is fire-and-forget (no ack), so shadow_report itself never moves off HTTPS, where an HTTP status confirms persistence. Reconnect is exponential backoff from `PIGEON_WS_BACKOFF_BASE_SEC` (1s), doubling, capped at `CONFIG_PIGEON_WS_RECONNECT_MAX_DELAY_SEC` (default 300s), ±25% jitter, reset to base once a connection survives its first app-level pong. One socket per pigeon is enforced server-side (dovecote's `objects/ws.rs`); a rival connection stealing the slot closes this device's socket with code 4009, which this library treats like any other drop and reconnects into.

**Hard-won gotcha, preserved here on purpose**: `pigeon_ws_teardown()` always calls `websocket_disconnect()` itself, unconditionally, rather than trusting Zephyr's own `websocket_recv_msg()` to have already unref'd its context on a server-initiated CLOSE. That trust used to be the code, and it was wrong — the vendored `zephyr/subsys/net/lib/websocket/websocket.c` checks `ctx->message_type == WEBSOCKET_FLAG_CLOSE` (exact equality, not a bitwise `&`) before running its own internal-disconnect/unref path, but RFC 6455 sec 5.5.1 forbids fragmenting control frames, so any real CLOSE frame from a compliant peer also carries `WEBSOCKET_FLAG_FINAL`, making `message_type` `CLOSE|FINAL` (0x09) — which that exact-equality check can never match (0x09 != 0x08). Confirmed empirically (a native_sim harness with temporary ref/unref tracing on a scratch copy of the gitignored vendored file showed exactly one `ref()` and zero `unref()` calls across a full connect→server-close→reconnect cycle). In practice this makes the library's own internal-disconnect path dead code for every real peer, and silently leaked the sole `CONFIG_WEBSOCKET_MAX_CONTEXTS` slot on every server-initiated close — reproduced as a permanent post-churn `"upgrade handshake failed: -17"` (EEXIST) wedging every subsequent reconnect. Fixed by having `pigeon_ws_teardown()` call `websocket_disconnect()` (which unrefs via the *outer* close path, unaffected by the buggy check) itself every time, regardless of how the socket went down. Confirmed fixed on real ESP32-C6 hardware via a live socket-steal test (device saw the close, reconnected in ~1s, reclaimed the socket).

The `pigeon_json_escape()` shared helper (`pigeon_core.c`, declared in `pigeon_internal.h`) was promoted out of `pigeon_https.c`/`pigeon_coap.c` (which each carried an identical private copy) specifically because `pigeon_ws.c` would otherwise have needed a third copy; it's now RFC 8259 control-char compliant (0x00-0x1F, `\n`/`\r`/`\t` via shorthand, `\u00XX` otherwise) rather than only escaping `"`/`\` — found because a raw control byte in a telemetry value used to produce invalid JSON that HTTPS/CoAP could shrug off as one failed report, but over `pigeon_ws.c`'s shared persistent socket got the whole connection closed by dovecote's strict `serde_json` parse (code 4003), taking `shadow_update` push delivery down with it.

`src/pigeon_fatal.c` (added 2026-07-23, `CONFIG_PIGEON_REBOOT_ON_FATAL`, task #45) and `src/pigeon_watchdog.c` (same date, `CONFIG_PIGEON_WATCHDOG`, task #15/#45) — the wedge-recovery mitigation for task #15's real-hardware finding: `ws_init` (see `pigeon-examples`) hard-panics after 42-60 minutes of WS/HTTPS uptime under WiFi reconnect churn, a rare ecall-based assert deep inside Espressif's closed-source `libnet80211.a` blob (symbol-resolved trace, repro profile, and both soaks' heap data all in `pigeon-examples`' `docs/upstream-issues/hal_espressif-libnet80211-wifi-thread-panic.md`, drafted for Justin to file upstream — not posted). Two independent hardware soaks (`sys_heap_runtime_stats_get()`/`malloc_runtime_stats_get()` on both plausible heaps) ruled out resource exhaustion as the trigger: `CONFIG_HEAP_MEM_POOL_SIZE` still had ~14KB free at crash time, and `CONFIG_COMMON_LIBC_MALLOC_ARENA_SIZE` (the arena the crash actually traces into) showed zero bytes ever allocated across a full 60 clean minutes. This is a latent vendor bug, not something sizing can fix — the only available mitigation on this side is detecting the resulting wedge and recovering.

Two independent, complementary layers, in priority order:
- **`CONFIG_PIGEON_REBOOT_ON_FATAL` (primary)**: overrides Zephyr's weak `k_sys_fatal_error_handler()` (documented app-overridable policy hook, `zephyr/include/zephyr/fatal.h`) to `LOG_PANIC()` + `pigeon_reboot()` instead of the default `arch_system_halt()` (locks interrupts, spins forever — confirmed on real hardware as total serial silence for over an hour, following exactly the kind of fatal error this bug produces). This is the layer that actually fixes the diagnosed failure: hardware-verified via a `k_panic()` forced-fault test, reboot observed in ~200ms, repeatable across multiple cycles. It reboots through `pigeon_reboot()` rather than `sys_reboot()` because on an ESP32-C6 the latter does not come back: it leaves the part's analog register I2C master unclocked and the next image hangs in its clock init, before any console exists to say so (`src/pigeon_reboot.c` carries the mechanism).
- **`CONFIG_PIGEON_WATCHDOG` (secondary)**: wraps Zephyr's Task Watchdog subsystem (`CONFIG_TASK_WDT`) for a *different* failure shape — a silent liveness stall with no fatal error (kernel keeps scheduling, app-level progress just stops). One channel, fed by `pigeon_shadow_flush()` success (`pigeon_core.c`, transport-agnostic) and — `CONFIG_PIGEON_WS` only — WS pong receipt (`pigeon_ws.c`, higher-frequency, independent of `telemetry_interval`). Its hardware-watchdog fallback (meant as the interrupts-disabled backstop, now redundant with the fatal-hook above for THIS bug) is **known-broken on ESP32 as of this writing**: `zephyr/drivers/watchdog/wdt_esp32.c` passes a millisecond timeout straight into `wdt_hal_config_stage()` as raw hardware ticks with zero conversion (that HAL function's own doc says ticks; the driver even defines the unused conversion constants it would need) — confirmed by comparison against ESP-IDF's own reference task-watchdog code in the same vendored tree, which does convert. A forced interrupts-disabled hang did not recover within a confirmed 9.2-minute lower bound against an intended ~120ms deadline. Draft upstream report: `pigeon-examples`' `docs/upstream-issues/zephyr-wdt_esp32-missing-tick-conversion.md`. Deliberately not patched around here (would silently double-convert once upstream fixes it) — an honest, documented residual gap, not a blocker, since the fatal-hook layer already covers the failure this project actually hit.

See `samples/https_init` in the sibling `pigeon-examples` repo for the HTTPS reference consumer (`src/shadow.c` fetches the shadow, applies `target_config` — app-defined `log`/`telemetry_interval`/`reboot` fields, the pigeon library itself doesn't parse `target_config`, see below — and polls on a loop driven by the shadow's own `telemetry_interval`), and `samples/ws_init` for the `CONFIG_PIGEON_WS`/`CONFIG_PIGEON_REBOOT_ON_FATAL`/`CONFIG_PIGEON_WATCHDOG` reference consumer.

## Feature-parity gaps (noted 2026-07, not yet addressed)

Comparing against Circuit Dojo's "Lion" IoT server (https://www.circuitdojo.com/posts/introducing-lion-iot-server) and, more importantly, against what **AWS IoT customers** — the actual target market — already expect from AWS IoT Core (Device Shadow, Jobs, Device Defender, fleet provisioning). Lion's specific protocol choices are one data point, not a spec to copy verbatim; weigh each gap against the AWS IoT mental model, not Lion's.

Confirmed via `~/pidgeiot/capsules/src/lib.rs` and `~/pidgeiot/dovecote/src/lib.rs`: **none of the following exist on the backend yet** (grepped for `telemetry`, `generation`/`command`, `log_stream`/`dictionary`, `firmware`/`ota`/`block2` — zero hits). These are backend gaps, not just device-firmware gaps — device code can't usefully be written against endpoints that don't exist.

- ~~**Telemetry ingestion**: no endpoint at all.~~ **Resolved 2026-07-15**: `POST <endpoint>/telemetry` (`report_telemetry_device`, dovecote) + `pigeon_set_shadow_param()`/`pigeon_shadow_flush()` (device). Latest-value-per-key store, not a time-series log — a history/range-query table is a deliberately deferred follow-up, as is a `fancier` display view.
- ~~**Command execution with ack**: no device-side ack path back to the platform.~~ **Resolved 2026-07-15**: `POST <endpoint>/shadow` (`report_shadow_device`, dovecote) + `pigeon_shadow_report()` (device), called from `https_init`'s `shadow_sync()` after applying `target_config`. Still no formal command queue beyond `target_version`/`current_version` as an implicit generation counter (the `"reboot": true` one-shot-command pattern in `shadow.c`) — AWS IoT's Jobs service remains the closest analog worth studying if a real queue is wanted later.
- ~~**Log streaming**: no endpoint, no dictionary/token-compressed log encoding wired up.~~ **Resolved 2026-07-17**: `pigeon_log_backend.c` (`CONFIG_PIGEON_LOG_UPLOAD`, opt-in) + dovecote's `POST <endpoint>/logs` — dictionary-mode encoding, hardware-verified e2e (15 chunks decoded, byte-matched against serial). DO-local ring buffer only, no durable/Postgres-backed log store (deliberate — this is a rolling debug buffer).
- ~~**OTA / firmware rollout**: ... no remote fetch-and-flash path ... no backend endpoint to serve images or track fleet rollout state.~~ **Mostly resolved 2026-07-18-20, task #23-24**: backend has R2-backed firmware storage + Range-chunked device download + shadow-embedded firmware targets; `pigeon_fota.c` (`CONFIG_PIGEON_FOTA`) does the device-side download/verify/schedule/reboot. Hardware e2e (real nRF9160) got through download, sha256 verify, MCUboot test-swap scheduling, shadow convergence report, and graceful reboot — the still-open pieces are: confirming a post-reboot device re-authenticates and converges cleanly (blocked as of 2026-07-20 on a stale-token OTA test artifact, see dovecote notes in `~/pidgeiot/CLAUDE.md`), and the deliberate unconfirmed-image MCUboot-revert test (never yet exercised). Dev-signing-key-in-use for MCUboot image signing is a known, documented, not-yet-fixed prod-readiness gap.
- **Auth model**: current transport is HTTPS + a per-pigeon Ed25519 keypair with an opaque binary bearer token (see `get_shadow_device`/`verify_device_token`, not JWT as of 2026-07-15). Lion uses PSK+DTLS for bandwidth reasons on sleepy NB-IoT devices; AWS IoT's primary device auth is X.509 mutual TLS (though custom authorizers are supported). Worth deciding deliberately rather than drifting — per-device-keyed bearer tokens over HTTPS is a reasonable AWS-IoT-adjacent choice already, not obviously wrong.
- **RBAC**: dovecote has basic user-level auth (`require_auth`) and per-pigeon ACL rows, but no granular role model has been checked against what AWS IoT's Device Defender/policy model expects.
- ~~**Persistent/real-time channel**: backend-only, this library has no WS transport or client yet.~~ **Resolved 2026-07-20, task #33**: `pigeon_ws.c` (`CONFIG_PIGEON_WS`) implements the device side of dovecote's WebSocket endpoint (`GET /device/pigeons/:id/ws`, added 2026-07-19) — persistent connect/reconnect-with-backoff, device-owned ping keepalive, telemetry-over-WS with HTTPS fallback, and server-pushed `shadow_update` handling. Hardware-verified on real ESP32-C6 against staging, including a live socket-steal recovery test (see "Current state" above for the context-leak bug that test caught and fixed). The ESP32 `wifi_adapter` heap allocation warnings turned out not to be non-fatal after all under a long enough soak (a real hard panic at 42-60min, PidgeIoT task #15/#45) — see `pigeon_watchdog.c`/`pigeon_fatal.c` above for the diagnosis and mitigation.

## Build

This is a Zephyr **module**, not a standalone buildable app — `CMakeLists.txt` hard-fails if `ZEPHYR_BASE` isn't set (see its guard clause). It must be built as a dependency from within a Zephyr application/workspace (`west build`), not compiled directly in this repo.

- `zephyr/module.yml` wires the module into a Zephyr manifest (`west.yml`) via `build.cmake`/`build.kconfig`.
- `zephyr/Kconfig` exposes `CONFIG_PIGEON` (menuconfig gate), a mutually-exclusive choice between `CONFIG_PIGEON_CONNECTOR_COAP`, `CONFIG_PIGEON_CONNECTOR_HTTPS`, `CONFIG_PIGEON_CONNECTOR_MQTT` and `CONFIG_PIGEON_CONNECTOR_NIDD` (NIDD's own knobs are `PIGEON_NIDD_CLAIM_KEY`, `_DEDICATED_CID`, `_RAI_IDLE_MS`, `_REPLY_WAIT_SEC`, `_SHADOW_WAIT_SEC`, `_THREAD_STACK_SIZE`; plus, under MQTT, `PIGEON_MQTT_AUTH_CERT`/`_PSK` and the session knobs `_SEC_TAG`, `_TLS_PSK_SECRET`, `_TELEMETRY_QOS1`, `_RX_BUF_SIZE`, `_TX_BUF_SIZE`, `_THREAD_STACK_SIZE`, `_SHADOW_WAIT_SEC`, `_PUBLISH_TIMEOUT_SEC`, `_MAX_INFLIGHT`, `_RECONNECT_MAX_DELAY_SEC`, `_AUTH_BACKOFF_SEC`; keepalive is Zephyr's own `CONFIG_MQTT_KEEPALIVE`, which wants a deliberate per-target value), `CONFIG_PIGEON_ENDPOINT` (string, required whenever a connector is selected) and `CONFIG_PIGEON_TOKEN` (string, required on HTTPS and certificate-mode MQTT builds — the connectors that authenticate through a PSK handshake never read it), `CONFIG_PIGEON_LOG_LEVEL` (0-4), and (`depends on PIGEON_CONNECTOR_HTTPS`) `CONFIG_PIGEON_WS` plus its sub-options (`_RX_BUF_SIZE`, `_PING_INTERVAL_SEC`, `_RECONNECT_MAX_DELAY_SEC`, `_THREAD_STACK_SIZE`) — reuses the HTTPS connector's endpoint/token/sec_tag, no separate WS credentials.
- `.vscode/settings.json` expects clangd compile commands at `build/https_init/compile_commands.json` — a symlink at `build` points to `~/pigeon-examples/build`, the shared build dir of the `https_init` sample in the sibling `pigeon-examples` repo (`samples/https_init`), which pulls this module in via `ZEPHYR_EXTRA_MODULES`.

## Conventions

- 2-space indentation (no `.clang-format` yet — follow the existing style in `src/pigeon_core.c`).
- Public API lives in `include/pigeon.h` behind an `extern "C"` guard; keep new public symbols there, not in `src/`.
- Use Zephyr's own logging (`LOG_MODULE_REGISTER`/`LOG_INF`/`LOG_ERR`), gated by `CONFIG_PIGEON_LOG_LEVEL`, not `printf`.
